Indexing in MongoDB: how a database finds one row in a crore

The problem indexes solve, what an index really is on disk, why almost every database reaches for a B+ tree, every MongoDB index type with a step-through animation, and a decision guide for what to use when.

01

The problem: finding one document in ten lakh

Before the solution, feel the pain that created it.

You built a login route. It works perfectly in class with 50 test users. Then the product launches, the users collection crosses ten lakh documents, and the same route starts taking more than a second. Nothing in your code changed. What changed is how much data the query has to walk through.

Step 1 / 10
The real cost is not the comparison
A CPU can compare ten lakh strings in a few milliseconds. The expensive part is reading the documents from disk so they can be compared. Disks (even SSDs) serve data in fixed-size blocks called pages, and a full scan drags every page of the collection through memory. The problem is I/O, not CPU — and that is why the fix is a data structure, not a faster loop.

Why 'just add more RAM' is not the answer

MongoDB's storage engine keeps a cache in RAM, so a small collection that fits entirely in memory scans fast. But a scan still touches every document, so CPU time and cache pressure still grow linearly. And the moment the collection outgrows the cache — which happens to every successful product — each scan turns into thousands of disk reads. Linear cost is the enemy; we need a lookup whose cost barely grows as the data grows.

The everyday version of this problem

A railway station displays a coach position board: coach S7 stops at platform marker 9. Without it, you would walk along the entire 24-coach train reading numbers on every coach — a collection scan. With it, you read one small board and walk straight to marker 9. The board is not the train; it is a small, separately maintained structure that tells you where to look. That is exactly what an index is.

Quick check · 01
A collection has 20 lakh documents and no index on phone. find({ phone: '98…' }) finds a match in the 3rd document it reads. How many documents does MongoDB read in total?
find() returns all matches. Without an index there is no way to know the 3rd document was the only one, so the scan continues to the end. (Only findOne() or limit(1) would let it stop early.)
Quick check · 02
Why does a collection scan get dramatically slower once the collection outgrows the storage engine's RAM cache?
CPU cost also grows, but linearly and cheaply. The cliff comes from I/O: a scan that used to hit RAM now hits the disk for every page of the collection.
02

What an index is

A separate, sorted, pointer-carrying copy of one field — kept in sync on every write.

An index is not a setting that makes a collection faster. It is a second data structure that MongoDB builds and stores on disk next to the collection: the values of one or more fields, kept in sorted order, each paired with a pointer to the document that owns it.

—
  1. Same 8 documents, same query. But now an index on email exists: a separate, sorted list of every email, each with a pointer to its document. The collection itself is untouched and still unordered.
  2. Because the keys are sorted, the engine does not read from the top. It jumps to the middle: pooja. 'sneha' comes after 'pooja' alphabetically, so everything above pooja is eliminated in one comparison.
  3. Jump to the middle of what remains: riya. 'sneha' > 'riya' — eliminate riya and everything before it.
  4. Next: sneha. Match. And because the keys are sorted, the engine also knows the next key (vikas) is different, so it can stop — no need to look further. This stage is called IXSCAN.
  5. The index entry holds a pointer (a RecordId) to the real document. Follow it and read exactly one document off disk. This stage is FETCH.
  6. Done: 3 keys examined, 1 document read. For 8 documents that saves little. For 10 lakh documents, sorted search needs about 20 comparisons instead of 10 lakh reads — and a real B+ tree does even better, as the next section shows.
Step 1 / 6
Definition
An index is an ordered mapping from indexed value → location of the document, stored separately from the documents and updated automatically on every insert, update and delete. Because it is ordered, the database can find a value without reading everything, and can return documents in that order without sorting them.

Three things every index gives you

Fast equality lookups
find({ email: "x" }) — go straight to the matching key instead of scanning.
Fast range scans
find({ age: { $gte: 18, $lt: 25 } }) — find the first matching key, then walk forward through sorted neighbours until the range ends.
Free ordering
sort({ createdAt: -1 }) — the keys are already sorted, so MongoDB just reads them backwards. Without an index, a sort over a large result set happens in memory and can hit the 100 MB limit.

The price: every write now does extra work

The index must stay correct. When you insertOne() a user, MongoDB writes the document and inserts a key into every index on that collection. Update the email? The old key is removed and a new one inserted. Delete the user? Every index loses an entry. An index trades slower writes and more disk/RAM for faster reads. It is a trade, not free speed.

indexes: 3 → 4 structures updated per insert
💡
Every collection already has one index. MongoDB automatically creates a unique index on _id. That is why findById() in Mongoose is always fast, and why you have never had to think about it.
Quick check · 03
After creating an index on email, where are the documents themselves stored?
Creating an index never moves or reorders documents. The index is a second, sorted structure that points back to them by RecordId.
Quick check · 04
A collection has 6 indexes. What happens on one updateOne() that changes only the city field, which is covered by 1 of those indexes?
An index only changes when an indexed field's value changes. Unrelated indexes stay as they are — but a change to a field that appears in many indexes pays for each one.
03

Why databases use B+ trees

The disk works in pages. The B+ tree is the data structure that respects that.

The last section showed the idea: keep keys sorted, search cleverly. But 'sorted' is not enough on its own — the shape of the structure has to match how disks and memory actually behave. This is where students usually get told 'MongoDB uses B-trees' and nothing more. Let's see why.

—
  1. A sorted list already lets us binary-search. So why not just store index keys as one big sorted array on disk? Because the disk does not give you 'one key' — it gives you a whole page (typically 4–32 KB) at a time. Here: 16 keys, 4 per page.
  2. Binary search for 51 starts in the middle: key 23, which lives in page 2. One disk read. 51 > 23 → look right.
  3. Middle of the right half: key 37, in page 3. Second disk read. 51 > 37 → look right again.
  4. Key 51 is in page 4. Third disk read to reach it. Binary search is clever about comparisons, but careless about pages: it hops across the disk, touching a new page on almost every step. With a crore of keys that is ~24 page reads per lookup.
  5. Now the same keys arranged as a B+ tree. The root page holds just three signpost keys (20, 33, 48) that tell you which leaf page to open. Each leaf page holds a run of sorted keys, and leaves are chained together.
  6. Read the root (one page — and since every query starts here, it is always in RAM, so effectively free). 51 ≥ 48 → follow the last pointer.
  7. Open leaf page 4: 51 is there. Two page reads total, one of them cached. The tree is shaped around the fact that disks work in pages: make each node exactly one page, pack it with as many keys as fit, and the tree stays very flat.

The insight in one sentence
A binary tree asks one question per disk read. A B+ tree packs hundreds of questions into the same disk read, so it needs far fewer reads. Fan-out is the whole trick.

B-tree vs B+ tree — the difference that matters for range queries

Both are wide, balanced, page-sized trees. The difference is where the data lives. In a B-tree, every node stores keys and their values, so a key you are looking for can be found in an internal node and the search stops early. In a B+ tree, internal nodes hold only routing keys; all the real key → pointer pairs live in the leaves, and the leaves are linked together in sorted order.

That second design wins for databases because (1) internal nodes without values can hold more keys per page, so the tree is even flatter, and (2) a range query like age between 18 and 25 becomes: find the first leaf, then walk the chain — no bouncing back up through the tree.

💡
What MongoDB actually uses. The default storage engine, WiredTiger, stores both collections and indexes as B-trees whose internal pages hold only keys and child references and whose leaf pages hold the key/value pairs — i.e. the B+ tree layout described here. The MongoDB docs still say 'B-tree'; the layout is the one that matters, and that layout is B+.
Quick check · 05
A B+ tree index has 1 crore keys, and each page holds about 250 keys. Roughly how many page reads does a single lookup need?
log₂(10⁷) ≈ 24, but a B+ tree's height is logfan-out(n): 250³ ≈ 1.5 crore, so 3 levels cover it. Root and second level almost always sit in the cache, leaving one real disk read.
Quick check · 06
Why does a B+ tree keep all real data in the leaves and link the leaves together, instead of storing data in every node like a plain B-tree?
Data-free internal nodes hold more keys per page (flatter tree), and the linked leaves turn any range or sort into a straight sequential walk.
04

B+ tree: exact working, insert and delete

The same rules your DBMS textbook uses (Korth), animated step by step.

You now know why the B+ tree wins. This section is the how: the rules a node obeys, how a key is added, how one is removed, and how the tree keeps itself balanced without anyone rebuilding it. Every walkthrough below is computed live by a real B+ tree implementation — not hand-drawn frames — so what you see is what the algorithm does.

Anatomy and the rules of the game

Rules for this demo (order 4 — max 3 keys per node)

Every node holds at most 3 keys. A node with 4 keys has overflowed and must split.

Leaf nodes must keep at least 2 keys (⌈3/2⌉). Internal nodes must keep at least 1 key, i.e. 2 children (⌈4/2⌉). Falling below the minimum is underflow. The root is exempt from minimums.

Internal keys are signposts: the pointer to the left of key k leads to values < k; the pointer to its right leads to values ≥ k. Real data (key → RecordId) lives only in leaves, which are linked in sorted order.

💡
In a real index a node is a whole disk page holding hundreds of keys, so splits and merges are rare. We use 3 keys per node so that you can see them happen within a dozen inserts. The algorithm is identical.

Insert: search down, place, split up

Insertion always has the same three beats. Search from the root to the one leaf where the key belongs. Place the key in sorted position. If the leaf overflows, split it in half and push a separator up — and if that overflows the parent, split again, all the way up. The tree only gets taller when the root itself splits, which is why every leaf is always at the same depth.

⚠️
Common exam mistake. On a leaf split the separator is copied up (it stays in the leaf). On an internal split the middle key moves up (it leaves the node). Students who mix these up produce trees where a real key vanishes or a signpost is duplicated.

Delete: remove, then borrow or merge

Deletion is where B+ trees earn their reputation for being tricky, but it is only four cases. Remove the key from its leaf. If the leaf still meets the minimum, done. If not, borrow a key from an adjacent sibling that has spare keys and fix the separator in the parent. If neither sibling can spare one, merge with a sibling and delete the separator from the parent — which may make the parent underflow, so repeat one level up. If the root ends up with zero keys, drop it: the tree gets shorter.

Starting from the tree the inserts built, delete 30 → 80 → 20 → 50. Each one triggers a different case, in order of difficulty.

Quick check · 07
A leaf with keys [20 25 30] receives 27 and overflows. After the split, which key appears in the parent, and does it also remain in a leaf?
The overflowed leaf [20 25 27 30] splits into [20 25] and [27 30]. The right leaf's first key, 27, is copied to the parent as a separator and remains in the leaf, because leaves hold the actual data. Only on an internal split does the middle key move up.
Quick check · 08
You delete key 50 from a leaf, and 50 also appears in the root as a separator. The leaf does not underflow. What happens to the 50 in the root?
Search for 50 still works: it routes to the leaf where 50 would be, finds it absent, and returns nothing. Rewriting internal keys on every delete would cost extra page writes for no benefit.

Inside MongoDB: WiredTiger, RecordId and the two trees

What actually happens between find() and the bytes on disk.

Students often picture 'the index points at the document' as a memory address. In MongoDB it is one B+ tree pointing into another. Seeing both trees makes explain() output obvious later.

IXSCAN → FETCH: two B+ tree walks← → keys also work
db.users.find({ email: "karan@x.com" })
stage
—
keys examined
0
docs examined
0
  1. In WiredTiger everything is a B+ tree — including the collection itself. The collection tree is keyed by RecordId (an internal 64-bit number). An index tree is keyed by the indexed value, and its leaf entries store the RecordId of the owning document.
  2. The query planner picks the email index. Start at that index's root page.
  3. 'karan' < 'neha' → take the left pointer to the first leaf.
  4. Leaf entry karan → RecordId 2. The IXSCAN stage is finished: it produced a RecordId, not a document.
  5. Now the FETCH stage: take RecordId 2 into the collection's B+ tree, starting at its root.
  6. 2 < 3 → left leaf.
  7. Found RecordId 2 → the full BSON document. Total: 1 key examined, 1 document examined, four page reads (two per tree, most of them cached).
  8. Remember this two-tree picture. It explains covered queries (if the index already has every field you asked for, FETCH is skipped entirely), why FETCH is the expensive stage (it is a second tree walk plus a document decode), and why _id lookups also go through an index — the _id index maps to RecordId first.
Step 1 / 8

Index keys are stored in a canonical, comparable form

WiredTiger cannot compare raw BSON fast enough, so MongoDB encodes each index key into a KeyString: a byte string designed so that plain memcmp ordering equals BSON ordering (numbers before strings, arrays element-wise, and so on). This is why a compound key { city: 1, age: -1 } can be stored in one B+ tree — the two fields are concatenated into one sortable byte string, with the sort direction baked into the encoding.

Where the cache fits

WiredTiger keeps a cache (by default about half of RAM minus 1 GB) of recently used pages from both trees. A page not in cache is read from disk. Practically: the top levels of every hot index live in RAM permanently, leaf pages come and go, and documents are the most likely thing to miss. That ordering is why the working set advice exists — your indexes should fit in RAM, even when your data cannot.

RecordId vs _id
_id is a user-visible field with its own unique index. RecordId is WiredTiger's internal key for the collection tree. find({ _id: x }) walks the _id index to get a RecordId, then walks the collection tree — exactly like any other indexed query. (Clustered collections, an opt-in feature, make _id the RecordId itself and skip the second walk.)
Quick check · 09
An index on { email: 1 } exists. The query is find({ email: 'a@x.com' }, { email: 1, _id: 0 }). Which stages run?
With _id excluded and only email projected, the index entry alone answers the query. Explain shows PROJECTION_COVERED above IXSCAN and totalDocsExamined: 0.
Quick check · 10
Which is generally the more expensive stage, and why?
IXSCAN reads small, densely packed, usually-cached pages. FETCH turns each RecordId into a separate collection-tree walk and a document read; a query returning 1 lakh documents does 1 lakh of them.

totalDocsExamined ÷ nReturned. If a query returns 10 documents but examined 1 lakh, the index is not selective for that query (or is missing). Aim for a ratio near 1. This single number catches most real-world slow queries.

Index builds and hidden indexes

Since MongoDB 4.2, all index builds are 'hybrid': the collection stays readable and writable while the index is built, with a brief lock at the start and end. On a big collection a build still costs CPU and I/O, so schedule it. Before dropping an index you are not sure about, hide it: the planner stops using it but it is still maintained, so un-hiding is instant if things get slower.

mongosh — hide before you drop
db.users.hideIndex("city_1_age_-1")   // planner ignores it; still updated on writes
// watch the app for a day…
db.users.unhideIndex("city_1_age_-1") // instant rollback
// or, if nothing slowed down:
db.users.dropIndex("city_1_age_-1")

// which indexes are actually used? (ops = times used since server start)
db.users.aggregate([{ $indexStats: {} }])
Quick check · 11
explain() shows nReturned: 12, totalKeysExamined: 12, totalDocsExamined: 50000. What is most likely going on?
Keys examined ≈ returned means the index did its job; docs examined ≫ returned means FETCH read far more than it kept — a second predicate is being applied after the fetch. Add that field to the index (or make it a compound index).
Quick check · 12
Which is the safest first step when you suspect an index on a production collection is unused?
A dropped index on a large collection may take a long time to rebuild and the app is slow meanwhile. Hiding keeps it maintained so restoring it is instant.

  1. The simplest index: one field, one direction. 1 means ascending, -1 descending. For a single-field index the direction does not matter for lookups — the tree can be read either way.
  2. Build: MongoDB walks the collection once, pulling out each document's age together with its RecordId. Six documents → six entries.
  3. The entries are sorted by key and written into a B+ tree. Two users share age 22 — duplicate keys are fine; ties are ordered by RecordId so each entry is still unique in the tree.
  4. find({ age: 22 }) → seek to the first 22 and walk while the key is still 22. Two entries → two RecordIds → two documents fetched. Never touches the other four.
  5. find({ age: { $gte: 25 } }) → seek to the first key ≥ 25, then walk the linked leaves to the end. Range queries are just 'seek, then scan neighbours'.
  6. sort({ age: -1 }) → read the tree backwards. No in-memory sort, no 100 MB limit — the index is the sorted order.
  7. Bonus: MongoDB can use the prefix of a compound index as if it were a single-field index. If { age: 1, city: 1 } exists, a separate { age: 1 } index is redundant — drop it.

7.5 · Geospatial index (2dsphere)

'Cafés near me', answered with a B+ tree.

2dsphere — cells and expanding rings← → keys also work
db.cafes.createIndex({ location: "2dsphere" })
  1. Latitude/longitude are two numbers, but a B+ tree sorts one key. So how do you index 'near me'? The trick is to turn a 2-D position into a single sortable number such that nearby places get nearby numbers.
  2. A 2dsphere index divides the globe into a hierarchy of cells (Google's S2 library). Each cell has an id, and ids are assigned along a space-filling curve so that cells close on the map are usually close in id. Each document's cell ids become its keys in an ordinary B+ tree.
  3. $near starts with the cell containing you and looks up documents in it — one seek. Chai Point is found.
  4. Not enough results yet, so it widens to the neighbouring ring of cells and seeks again. The index turns 'search a growing circle' into 'a handful of key-range scans'.
  5. One more ring reaches Sagar Gaire. Every match is checked against the real distance formula, and results come back sorted by distance.
  6. Beyond $maxDistance (3 km) the search stops — Bake&Co and Domino's are never examined. Use 2dsphere for real-world GeoJSON coordinates (spherical math); 2d exists for flat, legacy coordinate pairs. $geoWithin (inside a polygon) and $geoIntersects use the same cell trick.

08

What to use when

A decision guide, the ESR rule, and the index you should not create.

You now know every type. The skill that pays is choosing — and, just as often, not adding an index. Start from the queries, never from the schema: an index that no query uses is pure cost.

Single-field index

createIndex({ email: 1 }). Direction is irrelevant for a lone equality. If a compound index already starts with this field, you do not need this one.

Compound { A: 1, B: ±1 }

Equality field first, sort field second, in the sort's direction. The index serves find({A}), find({A}).sort({B}) and find({A, B}).

Compound, ESR order

Equality → Sort → Range. Putting the range before the sort forces an in-memory SORT stage. See the animation below.

Multikey (automatic)

Just index the array field. Keep at most one array field per compound index, and expect the index to be larger than the collection's document count.

Text index — or Atlas Search

{ title: "text", body: "text" } with weights for simple word search. For typo tolerance, autocomplete, facets or relevance tuning, use Atlas Search (Lucene) instead of fighting the text index.

2dsphere

Store GeoJSON { type: "Point", coordinates: [lng, lat] } — longitude first! — and index with "2dsphere". Use $near for sorted-by-distance, $geoWithin for 'inside this polygon'.

Unique (+ partial for optional)

{ unique: true }. If the field can be absent on many documents, add partialFilterExpression: { field: { $exists: true } } so missing values do not collide.

Partial index

Index only the hot slice (status: "active", deletedAt: null…). Smaller, faster, cheaper writes — but every query must repeat the filter.

TTL index

{ createdAt: 1 }, { expireAfterSeconds: N } on a Date field. Approximate timing, single field only. Perfect for sessions, OTPs, rate-limit counters, logs.

Wildcard index

{ "attributes.$**": 1 }. Great for catalogue-style documents. Remember it serves one path per seek and cannot be unique or TTL.

Hashed index

Only as a shard key on a monotonically increasing field (_id, timestamps). Equality only — never for range queries or sorting.

No index

Seriously. A monthly report over 50,000 documents is a fine COLLSCAN. Every index you add taxes every write forever. Indexes are for queries that run often, on collections that are big, where users are waiting.

  1. One query, three kinds of predicate: an Equality (status), a Range (amount > 500) and a Sort (createdAt). All three fields will go in one compound index — the question is in which order.
  2. Index A puts the range before the sort. Seek to open · >500: the matches are contiguous, good — but look at their dates: 09 Sep, 12 Sep. Not in date order. MongoDB must collect the matches and sort them in memory: an extra SORT stage, which fails above 100 MB.
  3. Why? Within status = open, index A is ordered by amount. A range on amount picks a slice of that order, and a slice of amount-order is not date-order. Whatever comes after a range in the index loses its ordering guarantee.
  4. Index B puts the sort field before the range. Within open the entries are already newest-first. Walk them in order and simply skip the ones with amount ≤ 500 (dim). Output comes out sorted — no SORT stage. A few extra keys examined, but zero memory sort and no 100 MB risk.
  5. The ESR rule: in a compound index put Equality fields first, then the Sort fields (in the sort's direction), then Range fields last. Equality shrinks the search to a contiguous block; sort keeps that block ordered; range trims it at the end. Almost every 'why is my query slow' in MongoDB is a violation of this order.
Step 1 / 5

How many indexes is too many?

There is a hard limit of 64 indexes per collection, but you should be worried long before that. Each index is a full B+ tree that every insert, update and delete must maintain, and that competes for the same RAM cache as your data. A practical heuristic for a write-heavy collection is 'as few as the hot queries need, usually under ten'. Use $indexStats to find indexes with zero operations, and remember that a compound index makes any index on its prefix redundant.

Design procedure that works in real projects

1. List the queries your app actually runs, with their filters, sorts and how often. 2. For each, write the fields as E / S / R. 3. Build the smallest set of compound indexes whose prefixes cover those shapes. 4. Verify each with explain(): IXSCAN, no SORT, docs examined ≈ returned. 5. Add unique/partial/TTL properties where the domain demands them. 6. Watch $indexStats in production and prune.

Index intersection: why it rarely saves you

MongoDB can use two single-field indexes for one query (an AND_SORTED / AND_HASH stage), by scanning both and intersecting the RecordIds. In practice the planner prefers one compound index almost every time, and for good reason: intersection reads two trees and then does set arithmetic, while a compound index does one seek. Do not build 'one index per field' and hope for intersection — build compound indexes for the query shapes you have.

The write side, honestly

Every index costs on three axes. Write latency: one more B+ tree insert (and possibly a page split) per index per write. Disk: indexes on big collections are often 20–40% of data size, and a text or multikey index can be larger than the collection. RAM: a hot index that does not fit in cache turns every write into a random disk read to find the page to modify. Check db.collection.stats().indexSizes and keep your hot indexes in memory.

⚠️
Mongoose autoIndex in production. With autoIndex: true (the default), every deploy triggers createIndex() for every schema index. On an existing index this is a no-op, but a changed definition builds a new index on a live collection at startup, on every instance. Turn it off in production and create indexes as a deliberate migration step.

10

Interview questions, practice and cheat sheet

Close the loop: explain it back, then do it with your own hands.

Questions you will be asked

Q1What is an index and why does it make reads faster?

A separate, sorted B+ tree of key → RecordId pairs maintained alongside the collection. Sorted keys plus a wide, shallow tree mean a lookup touches a handful of pages instead of every document.

Q2Why B+ tree and not a hash table or a binary search tree?

Hash tables give O(1) equality but no ranges or ordering. A BST holds one key per node, so its height — and its disk reads — is log₂ n. A B+ tree holds hundreds of keys per page, so height is logf n (3–4 levels for billions of keys), and its linked leaves make ranges and sorts sequential.

Q3What is the difference between a B-tree and a B+ tree?

B-tree: data in every node, search may stop early. B+ tree: data only in the leaves, internal nodes are routing keys only, leaves linked in order. Databases prefer B+ for higher fan-out and cheap range scans.

Q4Walk me through inserting a key that causes a split.

Search to the leaf; place the key in order; if the leaf exceeds max keys, split it in half, copy the right half's first key to the parent; if the parent overflows, split it and move its middle key up; if the root splits, create a new root — the only way the tree grows taller.

Q5And deleting a key that causes underflow?

Remove from the leaf. If below minimum: borrow from a sibling with spare keys (and fix the parent separator), else merge with a sibling and delete the separator from the parent; if the parent underflows, repeat upward; if the root empties, its only child becomes the root.

Q6What is the ESR rule?

In a compound index: Equality fields first, then Sort fields (in the sort's direction), then Range fields. It keeps matches contiguous and pre-sorted, avoiding an in-memory SORT stage.

Q7What is a covered query?

A query whose filter and projection use only fields in one index, with _id excluded (or also indexed). MongoDB answers from the index alone — no FETCH, totalDocsExamined: 0.

Q8Can MongoDB use an index for find({ age: 22 }) if the only index is { city: 1, age: 1 }?

No. Only left-to-right prefixes of a compound index are usable; age alone is not a prefix, so the 22s are scattered through the tree.

Q9Sparse vs partial index?

Sparse skips documents where the field is missing. Partial skips documents that fail an arbitrary filter (status: 'active', amount > 100…). Partial is the general, preferred form; sparse is the legacy special case.

Q10What does a multikey index do with an array, and what is its main restriction?

One entry per array element, all pointing at the same document. In a compound index at most one field may be an array in any given document.

Q11When would you choose a hashed index?

Essentially only as a sharded-cluster shard key on a monotonically increasing field, to spread inserts across shards. It supports equality only.

Q12How do you find slow queries and unused indexes in production?

Slow: the profiler / slowms logs plus explain('executionStats'), watching docs-examined vs returned and SORT stages. Unused: $indexStats; hide before dropping.

One paragraph to remember
An index is a sorted B+ tree of keys pointing at documents, kept in sync on every write. Its shape matches the disk (one node = one page, hundreds of keys, 3–4 levels), so reads cost a few page hits instead of a scan, and linked leaves make ranges and sorts free. Every index type is that same tree with a different key. Build indexes from your queries in ESR order, verify with explain(), and never forget that each one taxes every write.
