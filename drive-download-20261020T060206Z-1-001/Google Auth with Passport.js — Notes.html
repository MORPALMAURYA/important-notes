Login with Google, built from first principles

What OAuth actually is, what Passport.js does for you, and how one click turns into a logged-in user — with the "already registered? log in : register" logic wired up in Express and MongoDB.

Node.js Express Passport.js OAuth 2.0 / OIDC MongoDB JWT
01
Why OAuth exists
The problem first — then the protocol makes sense

Imagine a photo-printing app that wants your Google Photos. The naive way: you type your Google email and password into the printing app. Now that app can read your Gmail, delete your Drive, change your password — everything. And you can't take access back without changing your password everywhere.

OAuth fixes this. Instead of sharing your password, Google hands the app a limited, revocable key — "this app may read your photos, nothing else, until you revoke it." Your password only ever goes to Google.

Key Concept

OAuth 2.0 is a delegated authorization framework: it lets an app act on a user's behalf with limited permissions, without ever seeing the user's password. Think of a hotel key card — it opens your room for three nights, not the whole hotel forever.

Authentication vs Authorization

WhatAuthentication (AuthN)Authorization (AuthZ)

💡

"Login with Google" is technically OpenID Connect — a thin identity layer built on top of OAuth 2.0. When you request the openid/profile/email scopes, Google also tells you who the user is. Most people (and most interviewers) just say "OAuth", but knowing this distinction is an instant plus point.

03
What is Passport.js
Authentication middleware that hides the OAuth plumbing

You could implement OAuth by hand: build the Google URL, generate and verify state, POST the code to Google's token endpoint, call the userinfo API, handle every error. Passport.js does all of that for you and gives you one place to write your logic.

Key Concept

Passport.js is authentication middleware for Express. Each login method is a plug-in called a strategy — passport-local for email/password, passport-google-oauth20 for Google, and 500+ others. Passport does not store users. It hands you the verified Google profile, and you decide what to do with your database.

The four pieces you'll touch

passport.use(new GoogleStrategy(options, verify))
Register the strategy once with your client ID, secret and callback URL.
passport.authenticate('google')
Route middleware. Without a ?code it redirects to Google; with a ?code it exchanges it and fetches the profile.
The verify callback — (accessToken, refreshToken, profile, done)
Your code. This is where "registered? log in : register" lives. Call done(null, user) when finished.
req.user
Whatever you passed to done() is attached here for the next handler.

By hand vs with Passport

JobBy handWith Passport
Build consent URLManually assemble query paramsAutomatic ✓
Exchange code → tokensPOST to oauth2.googleapis.com/tokenAutomatic ✓
Fetch profileGET userinfo with Bearer tokenAutomatic, normalized ✓
Find / create userYour codeStill your code (verify callback)
Issue session / JWTYour codePassport sessions, or your JWT

Login or register — the core logic

          
One endpoint, two outcomes, decided inside the verify callback

        

      


      
With Google login there's no separate "Sign up" and "Sign in" button. The user clicks one button, and our server decides: seen this Google account before? Log in. Never seen it? Register, then log in. This pattern is called find-or-create.


      

        

          
Google profile arrives
profile.id, profile.displayName, profile.emails[0].value, profile.photos[0].value

        

          
User.findOne({ googleId: profile.id })
Look up by Google's stable ID — not by name, and not by email alone.

            

              
Found → registered
Skip creation. This is a login.

              
null → not registered
User.create({ googleId, email, name, avatar })

            

          

        

          
done(null, user)
Both paths end the same way: we have a user document. Issue a session or JWT and redirect.

      


      

        
verify callback — find-or-create


async (accessToken, refreshToken, profile, done) => {
  try {
    // 1. Already registered? → log in
    let user = await User.findOne({ googleId: profile.id });
    if (user) return done(null, user);

    // 2. Not registered → register
    user = await User.create({
      googleId: profile.id,
      email: profile.emails[0].value,
      name: profile.displayName,
      avatar: profile.photos?.[0]?.value,
    });
    return done(null, user);
  } catch (err) {
    return done(err);
  }
}

      


      
Level up: account linking

      
What if Riya signed up last month with email + password, and today clicks "Continue with Google" with the same Gmail? The code above would try to create a second user and crash on the unique email index. The fix: if there's no googleId match, check for a verified email match and attach the Google ID to that existing account.

      

        
find → link → create


let user = await User.findOne({ googleId: profile.id });

if (!user) {
  const email = profile.emails?.[0]?.value;
  const emailVerified = profile._json?.email_verified;

  // Same verified email registered earlier with a password? Link it.
  if (email && emailVerified) user = await User.findOne({ email });

  if (user) {
    user.googleId = profile.id;
    await user.save();
  } else {
    user = await User.create({ googleId: profile.id, email, name: profile.displayName });
  }
}
return done(null, user);

      


      

        
⚠️

        
Never link accounts on an unverified email. If you trust any email a provider sends, an attacker could create an account elsewhere with the victim's email and take over their account in your app.

      


      

        
💡

        
Race condition: two quick double-clicks can both see null and both try to create. The unique index on googleId makes the second insert fail instead of creating a duplicate. For a fully atomic version, use findOneAndUpdate({ googleId }, { $setOnInsert: {...} }, { upsert: true, new: true }).

const mongoose = require('mongoose');

const userSchema = new mongoose.Schema({
  googleId: { type: String, unique: true, sparse: true }, // sparse: password users have no googleId
  email:    { type: String, required: true, unique: true, lowercase: true },
  name:     String,
  avatar:   String,
  password: { type: String, select: false },              // only for email/password users
}, { timestamps: true });

💡

        
Why sparse: true? A normal unique index treats a missing field as null, so the second password-only user would clash with the first. Sparse indexes skip documents that don't have the field.

      


      

        
src/config/passport.js


const passport = require('passport');
const { Strategy: GoogleStrategy } = require('passport-google-oauth20');
const User = require('../models/user.model');

));

Auth routes

          
Two routes start and finish the dance, two more use the result

        

      


      

        
src/routes/auth.routes.js


const router = require('express').Router();
const jwt = require('jsonwebtoken');
const passport = require('../config/passport');
const { requireAuth } = require('../middlewares/auth.middleware');

// Steps 1–2: start the flow → Passport redirects to Google
router.get('/google',
  passport.authenticate('google', {
    scope: ['profile', 'email'],
    prompt: 'select_account',
    session: false,
  })
);

// Steps 6–15: Google sends the user back with ?code=
router.get('/google/callback',
  passport.authenticate('google', {
    session: false,
    failureRedirect: `${process.env.CLIENT_URL}/login?error=google`,
  }),
  (req, res) => {
    // req.user = whatever the verify callback passed to done(null, user)
    const token = jwt.sign({ id: req.user._id }, process.env.JWT_SECRET, { expiresIn: '7d' });

    res.cookie('token', token, {
      httpOnly: true,
      secure: process.env.NODE_ENV === 'production',
      sameSite: 'lax',
      maxAge: 7 * 24 * 60 * 60 * 1000,
    });
    res.redirect(`${process.env.CLIENT_URL}/dashboard`);
  }
);

router.get('/me', requireAuth, (req, res) => res.json({ user: req.user }));

router.post('/logout', (req, res) => {
  res.clearCookie('token');
  res.json({ message: 'Logged out' });
});

module.exports = router;

If you choose sessions

      

        
session-based setup


const session = require('express-session');
const MongoStore = require('connect-mongo');

app.use(session({
  secret: process.env.SESSION_SECRET,
  resave: false,
  saveUninitialized: false,
  store: MongoStore.create({ mongoUrl: process.env.MONGO_URI }),
  cookie: { httpOnly: true, secure: process.env.NODE_ENV === 'production', sameSite: 'lax' },
}));
app.use(passport.initialize());
app.use(passport.session());

// After login: what to store in the session → just the id
passport.serializeUser((user, done) => done(null, user.id));

// On every request: id from session → full user on req.user
passport.deserializeUser(async (id, done) => {
  try { done(null, await User.findById(id)); }
  catch (err) { done(err); }
});

      


      

        
Key Concept

        
serializeUser runs once at login and decides what goes into the session (keep it tiny — the id). deserializeUser runs on every later request and turns that id back into a full user on req.user.

src/middlewares/auth.middleware.js


const jwt = require('jsonwebtoken');
const User = require('../models/user.model');

async function requireAuth(req, res, next) {
  const token = req.cookies.token;
  if (!token) return res.status(401).json({ message: 'Not logged in' });

  try {
    const { id } = jwt.verify(token, process.env.JWT_SECRET);
    req.user = await User.findById(id);
    if (!req.user) return res.status(401).json({ message: 'User not found' });
    next();
  } catch {
    res.status(401).json({ message: 'Invalid or expired token' });
  }
}

// Session version is one line: if (req.isAuthenticated()) return next();
module.exports = { requireAuth };

About state with JWT: Passport stores the state value in req.session. So if you enable state: true while using session: false, add express-session just for the OAuth handshake — or use a custom state store.

      


      
Behind a load balancer (EKS, Render, Nginx)

      
Your Node app receives plain HTTP from the load balancer, even though the user is on HTTPS. Passport then builds http://…/callback, Google sees a URI you never registered, and you get redirect_uri_mismatch — only in production.

app.set('trust proxy', 1); // believe X-Forwarded-Proto from the LB / ingress

new GoogleStrategy({
  clientID: process.env.GOOGLE_CLIENT_ID,
  clientSecret: process.env.GOOGLE_CLIENT_SECRET,
  callbackURL: '/auth/google/callback', // relative…
  proxy: true,                           // …resolved using the forwarded https
}, verify);

      


      

        
⚠️

Put both on the same parent domain — app.yourdomain.com and api.yourdomain.com — and set domain: '.yourdomain.com' on the cookie.

Interview questions

          
Tap a question, answer it out loud first, then check

        

      


      
Fundamentals


      
Q1What is OAuth 2.0? Is it authentication or authorization?Basic
        
OAuth 2.0 is an authorization framework: it lets a third-party app get limited, revocable access to a user's resources without the user sharing their password. Authentication (who the user is) comes from OpenID Connect, a layer on top that adds the id_token. "Login with Google" is OIDC in practice.


      
Q2Walk me through the Authorization Code flow end to end.Basic
        
User clicks login → our server redirects to Google with client_id, redirect_uri, scope, state → user logs in and consents → Google redirects back with a short-lived code → our server POSTs the code + client_secret to Google's token endpoint → gets an access token (and id_token) → fetches the profile → finds or creates the user in our DB → issues our own session/JWT → redirects to the dashboard.


      
Q3Why does Google send a code instead of the access token directly?Medium
        
The redirect travels through the browser (front-channel), where URLs end up in history, logs and Referer headers. The code is single-use, expires in minutes, and is useless without the client_secret. The real token is only handed out on the back-channel, server-to-server, where the secret proves the caller is really our app. (That's exactly why the old Implicit flow is deprecated.)


      
Q4Access token vs refresh token vs id_token?Basic
        
Access token: short-lived key to call Google APIs. Refresh token: long-lived, used to get new access tokens without user interaction (only with offline access). id_token: a signed JWT from OIDC that describes the user — meant for our app to read, not to call APIs with.


      
Q5What is the redirect_uri and why must it be pre-registered exactly?Basic
        
It's where Google sends the user (and the code) after consent. If Google accepted any URI, an attacker could craft a login link with their redirect URI and steal the code. Exact matching means codes only ever go to URLs we control.


      
Q6What is the state parameter for?Medium
        
CSRF protection. We generate a random value, store it in the user's session and send it to Google. Google echoes it back on the callback, and we reject the request if it doesn't match. Without it, an attacker can make your browser finish their OAuth flow, silently logging you into the attacker's account.


      
Q7What is PKCE and when do you need it?Advanced
        
Proof Key for Code Exchange. The client creates a random code_verifier, sends its hash (code_challenge) in the first redirect, and sends the raw verifier during the token exchange. Even if the code is intercepted, it can't be redeemed without the verifier. It's required for SPAs and mobile apps that can't keep a secret, and is now recommended for all clients.


      
Q8What are scopes? Which ones do you need for login?Basic
        
Scopes are the permissions the app requests, shown on the consent screen. For login: openid, profile, email. Follow least privilege — asking for Drive or Gmail access just to log in scares users and invites stricter Google verification.


      
Passport.js


      
Q9What is Passport.js and what is a strategy?Basic
        
Passport is authentication middleware for Express with a pluggable design. A strategy is one login mechanism packaged as a plug-in — local, Google, GitHub, JWT. Passport standardizes the interface: every strategy ends by calling your verify callback and putting the result on req.user.


      
Q10What does the verify callback do, and what is done?Medium
        
It runs after Passport has verified the user with Google and receives (accessToken, refreshToken, profile, done). It's where we map the Google identity to our own user (find-or-create). done(err, user, info) tells Passport the result: done(err) for a server error, done(null, false) to reject login, done(null, user) for success.


      
Q11Explain serializeUser and deserializeUser.Medium
        
Only used with sessions. serializeUser runs at login and decides what minimal data goes into the session — usually just the user id. deserializeUser runs on every subsequent request, takes that id from the session and loads the full user onto req.user.


      
Q12How do you use Passport without sessions?Medium
        
Pass session: false to passport.authenticate, skip passport.session() and serialize/deserialize. In the callback handler, sign your own JWT with req.user._id, set it as an httpOnly cookie and redirect. Later requests are verified by a JWT middleware.


      
Scenarios & design


      
Q13How do you decide whether to log in or register a Google user?Basic
        
Find-or-create inside the verify callback: findOne({ googleId: profile.id }). If found, it's a login. If not, create a user with the Google profile data and treat it as login too. One button, one endpoint, two outcomes. Back it with a unique index on googleId to prevent duplicates.


      
Q14Why look up by googleId and not by email?Medium
        
profile.id (the OIDC sub) is permanent and unique per Google account. Emails can change, Workspace accounts can be renamed or deleted and recycled. Email is still useful as a secondary lookup for account linking — but only when Google marks it verified.


      
Q15A user signed up with email/password and now clicks "Continue with Google" with the same email. What happens?Advanced
        
A naive find-or-create tries to insert a second user and fails with a duplicate-key error on email. The right approach is account linking: no googleId match → check email_verified → find by email → attach googleId to the existing user. Some apps ask the user to log in with their password first to confirm the link.


      
Q16Two requests try to register the same new user at once. How do you avoid duplicates?Advanced
        
Both can see null and both insert. A unique index on googleId makes the DB reject the second insert (E11000) — catch it and re-fetch. Or make it atomic with findOneAndUpdate({ googleId }, { $setOnInsert: {...} }, { upsert: true, new: true }).


      
Q17Where do you store the JWT after Google login, and why?Medium
        
In an httpOnly, secure, sameSite cookie. localStorage is readable by any JavaScript on the page, so a single XSS bug leaks every user's token. httpOnly cookies can't be read by JS; pair them with sameSite (and CSRF tokens for risky actions if needed).


      
Q18Why can't the React app call /auth/google with axios?Medium
        
The endpoint answers with a 302 to Google's HTML login page. An XHR would try to follow that cross-origin redirect silently, hit CORS, and even if it didn't, there's no way to render Google's page for the user. OAuth needs a top-level navigation: <a href> or window.location.


      
Q19It works on localhost but gives redirect_uri_mismatch in production. Why?Advanced
        
Usually one of: the production callback URL isn't registered in Google Cloud; or the app sits behind a load balancer/ingress that terminates TLS, so Express sees http and Passport builds http://…/callback. Fix with app.set('trust proxy', 1) and proxy: true on the strategy, or an absolute https callback URL.


      
Q20Do you need to store Google's access token in your database?Medium
        
Not for login. Once you've identified the user and issued your own session/JWT, Google's tokens can be discarded. Store them only if you'll call Google APIs later (Calendar, Drive) — and then encrypt the refresh token at rest, since it's a long-lived credential.


      
Q21When a Google user clicks Logout in your app, are they logged out of Google?Basic
        
No. Logging out clears our session or JWT cookie only — their Google session is separate. Next login, Google may skip the password and just show the account picker. If you stored tokens, you can also revoke them via Google's revoke endpoint.


      
Q22Your JWT is valid for 7 days. How do you force-logout a user right now?Advanced
        
Stateless JWTs can't be "deleted". Options: short-lived access tokens + refresh tokens stored server-side (revoke the refresh token), a denylist of token IDs in Redis checked by the middleware, or a tokenVersion field on the user that you bump and compare on every request.
