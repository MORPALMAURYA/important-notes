Real-time with Socket.IO

Why HTTP alone cannot build a chat app, what Socket.IO adds on top of WebSocket, how events carry data between client and server, and what breaks when you run more than one server.

Node.js Express Socket.IO v4 Redis adapter
01
The Problem
In HTTP the server can never speak first

Everything you have built so far with Express follows one rule: the client sends a request, the server sends a response, and the exchange is over. The server only talks when it is asked something.

That works for loading a page or saving a form. It fails the moment new data appears on the server and the client has no reason to ask for it.

Key Concept

Request-response is a pull model: data moves only when the client pulls it. Real-time needs a push model: the server sends data the moment it exists, without waiting to be asked.

The chat example

Riya sends a message to Aman. The server receives it and saves it. Now what?

Riya → POST /messages → Server
    ↓
Server saves the message ✓
    ↓
Server wants to tell Aman
    ↓
✗ No open request from Aman, so there is nothing to respond to
    ↓
Aman sees the message only after he refreshes

Workaround 1: Polling

The client asks GET /messages every few seconds. Most of those requests return nothing new, each one carries full HTTP headers, and a message still arrives late by up to one polling interval.

Workaround 2: Long polling

The client sends a request and the server holds it open until there is something to send. When the response arrives, the client immediately sends the next request. Messages arrive quickly, but every message still costs a full HTTP request, and the server is holding thousands of hanging requests.

WhatPollingLong pollingWhat we actually need
Who startsClient, on a timerClient, again after every responseEither side, any time
DelayUp to one intervalLowClose to zero
Wasted workMany empty responsesHeaders on every messageA few bytes per message
ConnectionNew one each timeReopened after each messageOne, kept open
💡

Both workarounds are the client pretending the server can push. Gmail chat and early Facebook chat ran on long polling, and the pain of running it at scale is why WebSocket was standardised in 2011.

02
The Solution
WebSocket gives the pipe, Socket.IO makes it usable

WebSocket

WebSocket is a protocol that keeps one connection open between client and server. Once it is open, either side can send a message at any time, with only a few bytes of overhead per message.

It starts as a normal HTTP request carrying an Upgrade: websocket header. The server replies with status 101 Switching Protocols, and from then on the same TCP connection speaks WebSocket instead of HTTP.

Why not use raw WebSocket directly?

Raw WebSocket only gives you send(string) and an onmessage handler. Everything a real app needs is left to you:

  • The connection drops on a network change, and nothing reconnects it.
  • There is no way to say "send this to everyone in room 42".
  • Every message is one unnamed string, so you must invent your own message format.
  • You cannot tell whether the other side received what you sent.
  • Some corporate proxies block WebSocket, and those users simply cannot connect.
Key Concept

Socket.IO is a library that sits on top of WebSocket and fills those gaps: named events, automatic reconnection, rooms and broadcasting, acknowledgements, and a fallback to HTTP long polling when WebSocket is blocked.

WhatRaw WebSocketSocket.IO
Message shapeOne string or binary blobNamed event + any JSON data ✓
ReconnectionWrite it yourselfBuilt in, with backoff ✓
Groups of clientsKeep your own arraysRooms and namespaces ✓
Delivery confirmationNoneAcknowledgement callbacks ✓
WebSocket blockedConnection failsFalls back to long polling ✓
Bundle size and overheadNothing extra ✓Client library + small per-packet metadata
⚠️

Socket.IO is not WebSocket. It adds its own packet format on top. A plain WebSocket client cannot connect to a Socket.IO server, and a Socket.IO client cannot connect to a plain WebSocket server. Both sides must use Socket.IO.

How a Socket.IO connection is established

Handshake over HTTP
The client sends a normal HTTP request. The server replies with a session ID (sid) and its ping settings.
Start on long polling
The connection works immediately over HTTP long polling, which gets through almost every network.
Upgrade to WebSocket
In the background the client tries to open a WebSocket. If it succeeds, the connection switches to it.
Connected
Both sides exchange events. Ping and pong packets detect a dead connection, and the client reconnects on its own.

The one-way alternative: Server-Sent Events (SSE)

Not every real-time feature needs two directions. A notification bell, a live cricket score or an AI answer appearing word by word only needs the server to push to the client. For that there is a simpler tool than WebSocket.

Key Concept

Server-Sent Events is a normal HTTP response that never ends. The client makes one GET request, the server replies with Content-Type: text/event-stream, keeps the response open, and writes a new chunk of text every time it has something to send. Data flows only from server to client.

server (Express)
app.get("/events", (req, res) => {
  res.setHeader("Content-Type", "text/event-stream");
  res.setHeader("Cache-Control", "no-cache");
  res.flushHeaders();

  // each message is "data: ..." followed by a blank line
  const timer = setInterval(() => {
    res.write(`data: ${JSON.stringify({ time: Date.now() })}\n\n`);
  }, 1000);

  // the client closed the tab: stop writing
  req.on("close", () => clearInterval(timer));
});
client (built into the browser)
const source = new EventSource("http://localhost:3000/events");

source.onmessage = (event) => {
  const data = JSON.parse(event.data);
  console.log(data.time);
};

No library is needed on either side. EventSource is a browser API, and it reconnects by itself when the connection drops. When the client needs to send something, it uses a normal fetch request.

WhatSSEWebSocket / Socket.IO
DirectionServer → client onlyBoth ways
ProtocolPlain HTTP, works with existing routes, auth cookies and proxiesSeparate protocol after an upgrade
DataText onlyText and binary
ReconnectionBuilt into the browserBuilt into Socket.IO, manual in raw WebSocket
Rooms, acknowledgementsNoneBuilt into Socket.IO
Use it forNotifications, live scores, dashboards, AI response streamingChat, multiplayer games, collaborative editing
💡

How to choose: if the client only listens, use SSE. If the client also sends frequently and you need rooms or acknowledgements, use Socket.IO. The word-by-word answers in ChatGPT-style apps are SSE, because the user sends one prompt and then only receives.

⚠️

Two SSE limits to know. EventSource cannot send custom headers, so a token in an Authorization header will not work; use a cookie. And over HTTP/1.1 a browser allows only 6 open connections per domain, so several tabs each holding an SSE stream can block your other requests. HTTP/2 removes that limit.

03
Implementing Socket.IO
One package on the server, one on the client, attached to your existing Express app
Step 1 — Install

Socket.IO ships as two packages. The server one goes in your backend, the client one in your frontend.

Terminal
# backend
npm install express socket.io

# frontend
npm install socket.io-client
Step 2 — Create the server

Socket.IO needs the raw Node HTTP server, because it has to handle the upgrade request itself. So you wrap the Express app in createServer and give that server to Socket.IO.

server.js
import express from "express";
import { createServer } from "node:http";
import { Server } from "socket.io";

const app = express();
const httpServer = createServer(app);

const io = new Server(httpServer, {
  cors: { origin: "http://localhost:5173" },
});

io.on("connection", (socket) => {
  console.log("connected:", socket.id);

  socket.on("disconnect", (reason) => {
    console.log("disconnected:", socket.id, reason);
  });
});

httpServer.listen(3000, () => {
  console.log("listening on :3000");
});
PieceValue usedWhat it does
createServer(app)httpServerThe real Node HTTP server. Express handles normal routes on it, Socket.IO handles its own path (/socket.io/).
new Server()ioThe Socket.IO server. It represents all connected clients.
cors.originlocalhost:5173Which frontend origin may connect. Needed whenever frontend and backend run on different ports or domains.
"connection"(socket) => {}Runs once for every client that connects. All listeners for that client are registered inside it.
socket.idrandom stringUnique ID for this connection. It changes on every reconnect, so never use it as a user ID.
⚠️

Call httpServer.listen(), not app.listen(). app.listen() creates a second, separate HTTP server that Socket.IO is not attached to. Your REST routes will work and every socket connection will fail.

Key Concept

io is the whole server: use it to talk to everyone or to a room. socket is one single client's connection: use it to listen to that client and to reply to that client.

Step 3 — Connect from the client
socket.js (frontend)
import { io } from "socket.io-client";

export const socket = io("http://localhost:3000");

socket.on("connect", () => {
  console.log("connected with id:", socket.id);
});

socket.on("disconnect", (reason) => {
  console.log("disconnected:", reason);
});

socket.on("connect_error", (err) => {
  console.log("could not connect:", err.message);
});
💡

Create the client socket once in its own file and import it wherever you need it. Calling io() inside a React component creates a new connection on every render.

Verify

Start the backend, open the frontend, and check both consoles. The same ID must appear on both sides. Stop the server and start it again: the client reconnects by itself and gets a new ID.

server  connected: Xk3f9aQ2LmB7dE1pAAAB
browser connected with id: Xk3f9aQ2LmB7dE1pAAAB
same ID on both sides → the connection is working ✓

04
What are Events?
A name plus some data, sent over the open connection

In REST you tell the server what you want with a method and a URL: POST /messages. On a socket there are no URLs, because there is only one open connection. So you label each message with a name instead. That named message is an event.

Key Concept

An event is a name (a string you choose) plus data. One side calls emit(name, data) to send it. The other side has already called on(name, handler) to listen for that exact name. If the names do not match, nothing happens and no error is thrown.

WhatRESTSocket.IO
How you address a handlerMethod + URLEvent name
Register a handlerapp.post("/messages", fn)socket.on("message:send", fn)
Trigger itfetch("/messages", …)socket.emit("message:send", data)
Who can triggerOnly the clientClient or server

Emit and listen

client
// send an event to the server
socket.emit("message:send", { roomId: "chat:42", text: "Hello!" });

// listen for an event from the server
socket.on("message:new", (message) => {
  console.log(message.from, message.text);
});
server
io.on("connection", (socket) => {
  // listen for an event from this client
  socket.on("message:send", (payload) => {
    console.log(payload.roomId, payload.text);
  });

  // send an event to this client
  socket.emit("welcome", { serverTime: Date.now() });
});

What data can an event carry?

Anything that can be turned into JSON: objects, arrays, strings, numbers, booleans. You can pass several arguments, and binary data such as a Buffer or ArrayBuffer is supported too. Functions, class instances, Map and Set do not survive the trip.

Built-in events

A few event names are fired by Socket.IO itself. You listen to them, you never emit them.

EventFired onWhen
connectionserver · ioA new client has connected. The handler receives that client's socket.
connectclient · socketThe client is connected. Also fires again after every reconnect.
disconnectboth · socketThe connection closed. The handler receives a reason string such as transport close or ping timeout.
disconnectingserver · socketJust before disconnect, while socket.rooms is still filled. Useful for "user left the room" messages.
connect_errorclient · socketThe connection attempt failed: server down, CORS rejected, or auth middleware refused.
⚠️

Do not use these names for your own events: connect, connect_error, disconnect, disconnecting, newListener, removeListener. They are reserved.

💡

Name events as resource:action, for example message:send, message:new, typing:start, room:join. With thirty events in a project, this is what keeps them readable. And in React, remove each listener in the effect cleanup with socket.off(name, handler), or the handler runs twice after a re-render.

05
How Events Communicate
Who receives an event depends on what you call emit on

The event name decides which handler runs. The object you call emit on decides who receives it. On the client there is only one choice, the server. On the server there are several.

The emit cheat sheet (server side)

CallReachesTypical use
socket.emit()only this clientReply to the sender: their own data, an error, a welcome message.
io.emit()every clientGlobal announcement, live visitor count.
socket.broadcast.emit()everyone except sender"Riya came online". Riya already knows.
io.to(room).emit()everyone in the roomA system message in a chat room.
socket.to(room).emit()room, except senderA new chat message, a typing indicator.
io.to(socketId).emit()one specific clientPrivate message. Every socket is automatically in a room named after its own ID.

Rooms

Key Concept

A room is a named group of sockets that exists only on the server. A socket enters with socket.join(name) and leaves with socket.leave(name), and it leaves every room automatically when it disconnects. The client cannot join a room by itself. It emits an event asking to join, and the server decides.

server
io.on("connection", (socket) => {
  socket.on("room:join", (roomId) => {
    // check here that this user is allowed in this room
    socket.join(roomId);
    socket.to(roomId).emit("room:user-joined", { id: socket.id });
  });

  socket.on("typing:start", (roomId) => {
    socket.to(roomId).emit("typing:start", { id: socket.id });
  });
});
💡

Give every user a personal room. On connect, call socket.join("user:" + userId). A user with three tabs open has three sockets, and io.to("user:" + userId).emit(...) reaches all three without you tracking socket IDs.

Acknowledgements

A normal emit is fire and forget: you do not know whether the other side processed it. Pass a function as the last argument and Socket.IO turns the event into a request with a response. The receiver gets that function as its last parameter and calls it with the result.

client
socket.emit("message:send", { roomId, text }, (response) => {
  if (response.ok) markAsSent(response.id);
  else showError(response.error);
});

// with a timeout, so the UI never waits forever
socket.timeout(5000).emit("message:send", { roomId, text }, (err, response) => {
  if (err) showError("Server did not respond in 5 seconds");
});
server
socket.on("message:send", async (payload, ack) => {
  try {
    const message = await Message.create({
      room: payload.roomId,
      text: payload.text,
      from: socket.data.userId,
    });

    ack({ ok: true, id: message.id });
    socket.to(payload.roomId).emit("message:new", message);
  } catch (err) {
    ack({ ok: false, error: "Could not save the message" });
  }
});

06
Middleware
A checkpoint every client passes before the connection is accepted

So far anyone who knows your server URL can connect and start emitting events. In Express you solve this with middleware that runs before the route handler. Socket.IO has the same idea, with one important difference in when it runs.

Key Concept

A Socket.IO middleware is a function registered with io.use() that receives (socket, next). It runs once per connection, during the handshake, before the connection event. Call next() to let the client in, or next(new Error(...)) to refuse it.

Client asks to connect
It sends its credentials along with the handshake.
Middlewares run in the order you registered them
Each one must call next(). If one calls next(err), the rest are skipped and the client receives connect_error.
io.on("connection") fires
Only clients that passed every middleware reach your connection handler.
Step 1 — Send the token from the client
client
const socket = io("http://localhost:3000", {
  auth: { token: accessToken },
});

socket.on("connect_error", (err) => {
  console.log(err.message);   // "unauthorized"
});
Step 2 — Verify it in a middleware
server
import jwt from "jsonwebtoken";

io.use((socket, next) => {
  try {
    const token = socket.handshake.auth.token;
    const payload = jwt.verify(token, process.env.JWT_SECRET);

    socket.data.userId = payload.sub;   // available in every handler
    next();
  } catch (err) {
    next(new Error("unauthorized"));
  }
});

io.on("connection", (socket) => {
  // only authenticated clients reach this point
  socket.join("user:" + socket.data.userId);
});
PieceValue usedWhat it does
auth{ token }Client option. Whatever you put here is sent with the handshake.
socket.handshake.auth{ token }Where the server reads it. socket.handshake.headers holds the cookies and other HTTP headers.
socket.data{ userId }A free object on each socket. Store who this connection belongs to, and read it later in any event handler.
next()no argumentPass to the next middleware, or to the connection event if this was the last one.
next(err)new Error("…")Refuse the connection. The client gets connect_error with the same message.
⚠️

Always call next. If a middleware returns without calling next() or next(err), the client is left waiting until its connection attempt times out.

The difference from Express middleware

WhatExpress middlewareSocket.IO middleware
Signature(req, res, next)(socket, next)
RunsOn every requestOnce, when the client connects
To rejectres.status(401).json(…)next(new Error(…))
Client seesA 401 responseA connect_error event
⚠️

io.use() does not run for each event. It proves who the user is, once. It does not prove that this user may join room chat:42 or delete a message. Check permissions inside the event handler every time.

Middleware for every incoming event

When you want a check on each event, for example logging or rate limiting, register a middleware on the socket itself with socket.use(). It receives the event name and its arguments as an array.

server
io.on("connection", (socket) => {
  socket.use(([eventName, ...args], next) => {
    console.log(socket.data.userId, "sent", eventName);

    if (isRateLimited(socket.data.userId)) {
      return next(new Error("too many events"));
    }
    next();
  });

  // an error passed to next() arrives here, the event handler is skipped
  socket.on("error", (err) => {
    socket.emit("app:error", { message: err.message });
  });
});
💡

Every reconnect runs the middleware again, because a reconnect is a new connection. If the access token expired in the meantime, set a fresh one with socket.auth = { token: newToken } on the client before it reconnects.

07
Problems While Scaling
Everything above works on one server. Here is what breaks on two.

A REST API scales easily: requests are short and stateless, so any server can answer any request. A socket connection is the opposite. It is long-lived and it belongs to one specific server process. Every scaling problem with Socket.IO comes from that one fact.

Problem 1: Events do not cross servers

Rooms live in the memory of each server process. Server 1 only knows about the sockets connected to Server 1.

Two servers behind a load balancer
The load balancer sent Riya's connection to Server 1 and Aman's to Server 2. Both joined room chat:42, but each server only recorded its own socket.
Step 1 / 6
Fix — Redis adapter

An adapter is the part of Socket.IO that delivers an emit to sockets. The default one only looks in local memory. The Redis adapter also publishes every emit to Redis, and every server is subscribed, so each server delivers to its own local sockets.

Terminal
npm install @socket.io/redis-adapter redis
server.js
import { createAdapter } from "@socket.io/redis-adapter";
import { createClient } from "redis";

const pubClient = createClient({ url: process.env.REDIS_URL });
const subClient = pubClient.duplicate();

await Promise.all([pubClient.connect(), subClient.connect()]);

io.adapter(createAdapter(pubClient, subClient));

// nothing else changes: this now reaches the room on every server
io.to("chat:42").emit("message:new", message);
⚠️

The Redis adapter forwards events, it does not store them. If Aman is offline when the message is emitted, he never receives it. Chat history must be saved in your database and fetched when the client connects again.

Problem 2: The handshake breaks without sticky sessions

Remember that a connection starts on long polling, which is several separate HTTP requests. If the load balancer sends the first request to Server 1 and the next to Server 2, Server 2 has never seen that session ID and answers 400 with Session ID unknown. The client keeps failing and reconnecting.

FixHowTrade-off
Sticky sessionsConfigure the load balancer to always route one client to the same server (cookie or IP based).Keeps the long-polling fallback. Needs load balancer configuration.
WebSocket onlyOn the client: io(URL, { transports: ["websocket"] }). One connection, so there is nothing to route twice.No sticky sessions needed. Users on networks that block WebSocket cannot connect.

Problem 3: State kept in server memory

A const onlineUsers = new Map() at the top of your file works on one server. On three servers you have three different maps, each with a third of the users. Anything that more than one server must agree on belongs in Redis or the database: online status, who is in which room, unread counts.

Problem 4: Every restart drops connections

A deploy restarts the process, and every socket on it closes. All of those clients reconnect at the same moment, which can overload the servers that are still running.

  • Shut down gracefully. On SIGTERM, call io.close() so clients are disconnected cleanly and reconnect to another server.
  • Roll the deploy. Restart one server at a time so only a fraction of users reconnect together.
  • Catch up on reconnect. The client sends the ID of the last message it saw, and the server returns everything after it from the database.
server.js
process.on("SIGTERM", () => {
  // disconnects every socket and closes the HTTP server
  io.close(() => process.exit(0));
});

Problem 5: Idle connections still cost memory

An idle REST user costs the server nothing. An idle socket user holds an open connection, a file descriptor and some memory the whole time. Fifty thousand quiet users are still fifty thousand open connections, so you plan capacity by connected users, not by requests per second.
