Who sent this request?

Your server already accepts requests and talks to a database. But every request that arrives looks the same — the server has no idea which human is on the other end. Today we fix that, and then decide what each identified user is allowed to do.

01
The problem — who sent this request?
Before we write a single line of auth code, feel the problem it solves

Three users are using your app right now — A, B and C. All three tap the same button, so all three send the same request to the same route on your server.

Fig 1 — the server receives requests, not people

The server sees three HTTP requests. It does not see A, B or C. HTTP is stateless — the server keeps no memory of who connected last time, and nothing in a plain request says who is holding the phone.

Key Concept

Stateless means every request is treated as a brand new stranger. Request number two knows nothing about request number one. If we want the server to recognise a user, the request itself has to carry the proof.

Why this actually matters

Take a banking app. A user asks to transfer ₹60,000:

Incoming request 
POST /api/transfer
Content-Type: application/json

{
  "to": "XYZ0001234",
  "amount": 60000
}

# Transfer 60,000 to XYZ0001234 — fine.
# But FROM whose account? The request never says.

Money has to leave someone's account. Without identity this endpoint is either useless or catastrophic. The same question shows up everywhere: whose cart is this, whose posts do I return, whose profile is being edited.

⚠️

The obvious fix — send userId in the body — is the classic beginner trap. The body is written by the client. Anyone can open Postman and put your id in it and empty your account. Never trust data the client can edit. Identity must be something the client cannot fake.

Definition

Authentication is the process of identifying the user who made the request.

Why can't the server simply remember who user A is after their first request?

02
Authentication vs authorization
Two different questions that students mix up in every interview

These two words look alike and are constantly confused. They answer completely different questions, and they run one after the other.

Key Concept

Authentication asks who are you?  ·  Authorization asks are you allowed to do this? You cannot check what someone is allowed to do until you know who they are — so authentication always runs first.

WhatAuthenticationAuthorization
The question Who is this user? Is this user allowed to do it?
Runs First After authentication
Checks Credentials or a valid token Role, ownership, permissions
Fails with 401 Unauthorized — "I don't know you" 403 Forbidden — "I know you, and no"
In our app Verifying the token on /api/orders Only role: "admin" may delete a product

A real example from a college: the guard at the gate checks your ID card and confirms you are a student — that is authentication. Inside, that same card does not open the staff room, because the card says student, not teacher — that is authorization.

💡

401 vs 403 is a favourite interview question. 401 means no valid identity was presented. 403 means the identity is fine, the permission is not.

03
Validation — check before you trust
The step that runs before we even ask who you are

Before identity, sanity. Validation asks a simpler question: is this data even usable? Is the email actually shaped like an email, is the password long enough, is amount a positive number and not the string "sixty thousand"?

Order of a protected request

Validation
Is the incoming data the right shape? → 400 Bad Request
Authentication
Who is sending this? → 401 Unauthorized
Authorization
Is this user allowed here? → 403 Forbidden
Controller
Only now do we touch the database and do the real work.
controllers/auth.controller.js 
// the simplest possible validation — do it before anything else
const { name, email, password } = req.body;

if (!name || !email || !password) {
  return res.status(400).json({ message: "name, email and password are required" });
}

if (password.length < 8) {
  return res.status(400).json({ message: "password must be at least 8 characters" });
}

// In a real project you would not write this by hand for every route.
// Use a schema library — zod, joi or express-validator — as middleware.
⚠️

The validation you wrote in React is UX, not security. Postman, curl and a script never open your form. If the only check lives in the browser, there is effectively no check. Validate on the server, always.

04
The student ID card
The whole token idea, in a story you have already lived

Think about joining a school or college.

First you fill an admission form — name, details, documents. The office verifies it and writes you into their register. A few days later they hand you an ID card. That card carries your roll number, your class, a photo, an expiry date, and the school's stamp or hologram.

Now watch what the card does. At the library gate, the computer lab, the swimming pool, the sports club, the ground — you show the card and you are let in. Nobody sends you back to the admission office. Nobody makes you fill the form again. The card is your proof, and every gate can check it on the spot.

That is exactly what a token does for your server.

At schoolIn our backend
Filling the admission formRegistration — POST /api/auth/register
Office verifies and records youServer validates and saves the user in the database
School issues an ID cardServer signs and issues a JWT
Roll number printed on the cardThe user's id inside the token payload
Stamp / hologram nobody can copyThe signature, created with a secret only the server has
Showing the card at the library gateSending the token with every request
Card valid till March 2027expiresIn — the token stops working after that
Lost card? Report it, get a new oneLogout / re-login issues a fresh token
Key Concept

The gatekeeper never calls the admission office. Everything needed to trust you is printed on the card itself, and the hologram proves it is genuine. That is why JWT auth is called stateless — the server does not have to store a session for you anywhere.

💡

Push the analogy one more step and you get authorization for free: a student card opens the library, a teacher card opens the staff room. Same card system, different role printed on it.

05
Inside a JWT
Three parts, two dots, and one very common misunderstanding

JWT stands for JSON Web Token. It is a long string that looks like random noise, but it is not random at all. Look for the two dots — they split it into three parts.

A real JWT 
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpZCI6IjY4ZjNhMWM5NGU3YjJkMDAxMmM5YWI0NSIsInJvbGUiOiJzdHVkZW50IiwiaWF0IjoxNzU2NzAzNDAwLCJleHAiOjE3NTczMDgyMDB9.Jz74pc6s1u5dKsQOWBkuKcfGXT4Mz3IVg2GiJBvDaYU

# header . payload . signature
PartHoldsWhat it is for
Header { alg, typ } Which algorithm signed this token. Usually HS256, and the type is JWT.
Payload { id, role, iat, exp } The actual data — the "claims". This is what your server reads to know who the user is.
Signature HMACSHA256(...) Header + payload signed with your secret key. This is the hologram — proof the token came from your server and was not edited.

Decode it yourself

The first two parts are just JSON, Base64URL-encoded. No key, no password, no special tool — the browser can read them. Paste any token below and see it open up.

JWT decoder — paste a token
⚠️

Base64URL is encoding, not encryption. A JWT is readable by anyone who has it — the user, a browser extension, anyone reading a log file. Never put a password, OTP, card number or Aadhaar inside a token.

Then what stops someone editing it?

Try it live: press Load edited token above. Someone took the student token, changed "role": "student" to "role": "admin", and re-encoded the payload. It decodes perfectly. It looks like a valid admin token.

But the signature was calculated from the original header and payload using a secret that only your server knows. Change one character of the payload and the signature no longer matches. When your server runs jwt.verify(), it recomputes the signature and sees the mismatch — the token is rejected.

Attacker edits payload → role: "admin"
    ↓
Server recomputes signature using its secret
    ↓
Computed signature ≠ signature on the token
    ↓
jwt.verify() throws → 401 Unauthorized ✅
Key Concept

A JWT is readable by everyone, forgeable by no one. Read access is public. Write access needs the secret. That single line explains almost every JWT rule you will ever be told.

Your teammate says "the payload is safe, it's encrypted". Are they right?

06
What goes inside the payload
Keep it small, keep it boring

Since the payload is public, the rule writes itself: put in the minimum the server needs to identify the user, and nothing else. In practice that is the user's id, and — if you have roles — the role.

FieldPut it in the token?Why
id / _idYesThe whole point — it tells the server which database document this request belongs to.
roleYesLets authorization run without an extra DB call. Not secret information.
iat, expAutomaticIssued-at and expiry. The library adds these for you when you pass expiresIn.
Password or its hashNeverIt would be public. This is the single worst JWT mistake.
Phone, address, Aadhaar, DOBNoPersonal data that anyone holding the token could read. Fetch it from the DB when needed.
Cart, orders, big objectsNoThe token travels with every single request. Keep it light.
utils/token.js 
const jwt = require("jsonwebtoken");

function signToken(user) {
  return jwt.sign(
    { id: user._id, role: user.role },   // payload — small on purpose
    process.env.JWT_SECRET,                // secret — never hardcode it
    { expiresIn: "7d" }                    // adds iat + exp for you
  );
}

module.exports = { signToken };
💡

A token is a photocopy taken at login time, not a live view of the database. If you promote a user to admin today, their old token still says student until it expires — and if you demote an admin, their old token still says admin. That is exactly why tokens should be short-lived.

08
Why we hash passwords
The one mistake that can end a product and a career

Registration means storing a user in your database. The tempting version looks like this:

users collection — the dangerous version 
{ "email": "riya@gmail.com",  "password": "riya@1234" }
{ "email": "aman@gmail.com",  "password": "sheryians123" }
{ "email": "neha@gmail.com",  "password": "sheryians123" }

# It works. Login is a simple ===. And it is a disaster waiting to happen.

Now list everyone who can read that column

  • Anyone who gets a copy of the database — a leak, a stolen backup, a public Mongo instance with no password on it.
  • Every developer, intern and DBA on your team, including the one who leaves next month.
  • Whatever log, analytics tool or error report accidentally captured a request body.

And here is the part students underestimate. People reuse passwords. sheryians123 is probably also Neha's email password, her Instagram password, maybe her bank password. If your little project leaks, you did not just lose your app's accounts — you handed over other people's lives. That is why this is treated as a serious offence and not a bug.

Key Concept

Hashing is a one-way street. You can turn a password into a hash, but you cannot turn a hash back into the password. So we never store the password — we store the hash. At login we hash the incoming password again and compare the two hashes. The server itself never knows your real password.

WhatEncoding (Base64)Encryption (AES)Hashing (bcrypt)
Reversible?Yes, by anyoneYes, with the keyNo, by design
Needs a key?NoYesNo
Used forSafe transport of data — JWT partsData you must read back laterPasswords — you never need them back

Why bcrypt and not MD5 or SHA-256

MD5 and SHA-256 are hashes too, but they were built to be fast. A modern GPU can try billions of guesses per second against them, and precomputed rainbow tables already contain every common password. Fast is exactly what you do not want here.

bcrypt is deliberately slow, and you control how slow with a cost factor. It also salts every password automatically — a random value mixed in before hashing. Look at Aman and Neha, who chose the same password:

bcrypt.hash("sheryians123", 10) — run twice 
# aman
$2b$10$GnnIMosW7uaOVRg98b9jOeBlf6ZQb6lmq1cLpTZo9y6fD/SgMypMe

# neha — same password, completely different hash
$2b$10$Ao8zemGb5v7Wbp/o8E.V/eGHZrT0Km.doIcku8ZxQpFNCUojLMqUu

Same input, different output, because each got its own random salt. An attacker cannot spot that two users share a password, and cannot crack a thousand accounts with one precomputed table — every account has to be attacked separately, slowly.

⚠️

Never hash on the client, never log a password, and never send the password or its hash back in a response. And do not invent your own hashing scheme — reversing your own "secret formula" is the first thing an attacker tries.

Two users pick the same password. Why do their bcrypt hashes look completely different?

bcrypt in practice
Two functions, and what that weird string actually contains
Step 1 — Hash on registration
hashing a password 
const bcrypt = require("bcryptjs");

const hashedPassword = await bcrypt.hash(password, 10);
//                                         ↑ cost factor (salt rounds)

// store hashedPassword in the database — never the plain one
Step 2 — Compare on login
checking a password 
const isMatch = await bcrypt.compare(password, user.password);
//                                     plain input    stored hash

if (!isMatch) {
  return res.status(401).json({ message: "invalid email or password" });
}

Notice we never "decrypt" anything. bcrypt.compare reads the salt out of the stored hash, hashes the incoming password with that same salt, and checks whether the results match.

Reading a bcrypt hash

SegmentValue in our exampleWhat it means
algorithm$2bWhich bcrypt version produced this hash.
cost$10210 rounds of work. Every +1 doubles the time to hash — and to attack.
saltGnnIMosW7uaOVRg98b9jOeThe 22-character random salt, stored right inside the hash so login can reuse it.
hashBlf6ZQb6lmq1cLpTZo9y6fD/SgMypMeThe actual result of hashing password + salt.
💡

Cost 10 is a sensible default — roughly 50–100 ms per hash. Slow enough to make brute force painful, fast enough that your login route still feels instant. Do not push it to 20 "for extra security" unless you enjoy 30-second logins.

models/user.model.js 
const mongoose = require("mongoose");

const userSchema = new mongoose.Schema({
  name:     { type: String, required: true, trim: true },
  email:    { type: String, required: true, unique: true, lowercase: true },
  password: { type: String, required: true, select: false },
  role:     { type: String, enum: ["user", "admin"], default: "user" }
}, { timestamps: true });

module.exports = mongoose.model("User", userSchema);
💡

select: false on the password means every normal query leaves it out automatically. You cannot leak a hash you never fetched. On login you ask for it explicitly with .select("+password").

11
The register route
Filling the admission form
controllers/auth.controller.js 
const bcrypt = require("bcryptjs");
const User = require("../models/user.model");
const { signToken } = require("../utils/token");

module.exports.register = async (req, res) => {
  const { name, email, password } = req.body;

  // 1. validate
  if (!name || !email || !password)
    return res.status(400).json({ message: "all fields are required" });

  // 2. is this email already admitted?
  const exists = await User.findOne({ email });
  if (exists)
    return res.status(409).json({ message: "email already registered" });

  // 3. hash — the plain password must never reach the database
  const hashedPassword = await bcrypt.hash(password, 10);

  // 4. create the user (the register entry)
  const user = await User.create({ name, email, password: hashedPassword });

  // 5. issue the ID card
  const token = signToken(user);
  res.cookie("token", token, { httpOnly: true });

  return res.status(201).json({
    message: "registered successfully",
    user: { id: user._id, name: user.name, email: user.email }
  });                                // ↑ never send the password back
};
💡

Notice the order: validate → check duplicate → hash → save → issue token. Every step is cheap protection for the step after it. And 409 Conflict is the honest status for "this email already exists", not 400.

12
The login route
Collecting a fresh ID card
controllers/auth.controller.js 
module.exports.login = async (req, res) => {
  const { email, password } = req.body;

  if (!email || !password)
    return res.status(400).json({ message: "email and password are required" });

  // password is select:false in the schema, so ask for it explicitly
  const user = await User.findOne({ email }).select("+password");

  if (!user)
    return res.status(401).json({ message: "invalid email or password" });

  const isMatch = await bcrypt.compare(password, user.password);

  if (!isMatch)
    return res.status(401).json({ message: "invalid email or password" });

  const token = signToken(user);
  res.cookie("token", token, { httpOnly: true });

  return res.status(200).json({ message: "logged in" });
};
⚠️

Both failures return the same message: "invalid email or password". If you say "user not found" for one and "wrong password" for the other, you have just built a tool that tells an attacker which emails are registered on your platform.

13
The auth middleware
The guard at every gate

This is where authentication actually pays off. One small middleware sits in front of every protected route, checks the card, and hands the route a ready-made req.user.

middlewares/auth.middleware.js 
const jwt = require("jsonwebtoken");

module.exports.isLoggedIn = (req, res, next) => {
  // the card can arrive as a cookie or an Authorization header
  const token =
    req.cookies.token || req.headers.authorization?.split(" ")[1];

  if (!token)
    return res.status(401).json({ message: "please login first" });

  try {
    // verify = recompute the signature and check expiry
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    req.user = decoded;        // { id, role, iat, exp }
    next();
  } catch (err) {
    return res.status(401).json({ message: "invalid or expired token" });
  }
};
⚠️

Use jwt.verify(), never jwt.decode(). decode() only reads the payload and checks nothing — no signature, no expiry. Using it to authenticate means any string a user invents becomes a valid login.

Adding authorization on top

Authentication is done. Now the role check — the same card, a different gate:

middlewares/role.middleware.js 
module.exports.allow = (...roles) => (req, res, next) => {
  if (!roles.includes(req.user.role))
    return res.status(403).json({ message: "you are not allowed to do this" });
  next();
};
routes/product.routes.js 
// authentication → authorization → controller
router.delete(
  "/products/:id",
  isLoggedIn,          // who are you?      → 401
  allow("admin"),      // allowed to do it? → 403
  deleteProduct
);

// inside deleteProduct you can now trust req.user.id — it came from
// a signed token, not from the request body.

Where the token lives
Two places to keep the card, and why one is safer
WhatlocalStoragehttpOnly cookie
Sent automaticallyNo — you attach it by hand on every callYes, the browser attaches it
Readable by JavaScriptYes — so any injected script can steal itNo — JS cannot touch it
Works withMobile apps, third-party APIsBrowser apps on your own domain
Needs care aboutXSSCSRF — handled with sameSite
production cookie options 
res.cookie("token", token, {
  httpOnly: true,                    // JS cannot read it
  secure: process.env.NODE_ENV === "production",  // HTTPS only
  sameSite: "lax",                   // blocks most CSRF
  maxAge: 7 * 24 * 60 * 60 * 1000   // 7 days, matching the JWT
});

// logout = take the card back
res.clearCookie("token");
💡

Here is the honest limitation of stateless auth: because the server stores nothing, it cannot un-issue a token. If someone steals a valid token, it works until it expires — clearing the cookie only clears that browser. The industry answer is short-lived access tokens plus refresh tokens, which is our next session.

Build this yourself

1 — Register and login
A fresh Express + Mongoose project with /register and /login. Hash with bcrypt, issue a JWT in an httpOnly cookie. Check in Compass that no plain password was ever saved.
2 — Protect a route
Add GET /profile behind isLoggedIn, returning the logged-in user from req.user.id. Call it in Postman without a token and confirm you get 401.
3 — Add a role
Give one user role: "admin", add DELETE /products/:id behind allow("admin"), and confirm a normal user gets 403 while the admin gets through.
4 — Break it on purpose
Copy your token into the decoder in section 05, change the role to admin, re-encode it and send it. Watch the server reject it — then explain out loud why.
